# Implementation Plan: GGUF Slice 1 (Qwen2 with F16, Q8_0 and Q4_0)

**Date:** 2026-10-16  
**Status:** Implementation integrated. The independent proof found, and allowed us to fix, a Q4 addressing error at large indices. See the factual update at the end of this plan.

## Goal of Slice 1

Implement support for the GGUF format for the Qwen2 architecture with the data types F16, Q8_0 and Q4_0, including reading GGUF files, type-specific quantization, integration with existing models and parity verification.

## Author's Decisions Applied

- The inline half scale becomes a separate float (Q4_0/Q8_0): Q4_0 from 18 to 20 bytes per block (+11%), Q8_0 from 34 to 36
- mmap per tensor (avoids the 2GB limit)
- F16 widened to F32 on load (doubles the memory of those weights)
- Q8_0 embedding stays quantized; each looked-up embedding is widened to F32, because the residual does not support F32 x I8 (without duplicating the whole weight in memory)
- SentencePiece out (only gpt2/byte BPE)
- New Panama F32xQ8 kernel in PanamaTensorOperations (no I8xQ8)
- Plan order: GGUF reader + test writer, Panama F32xQ8 kernel, weight parity, tokenizer, end to end
- Handling of combinations without a kernel: delegate to Panama or throw a clear error (decision based on how NativeSimdTensorOperations handles combinations without a kernel)

### Known Risks and Mitigations
1. **Dimension order:** Confirmed on the real Q4_0 GGUF; the GGML dimensions are reversed for `TensorShape`. The test against the F16 model still waits for the real files.
2. **Tokenizer:** Reproduce exactly the one from tokenizer.json (mitigation: tokenizer parity test)
3. **Special tokens:** Convert to *added tokens* for correct segmentation of the chat template
4. **Chat template:** Enter `PromptSupport` as in `tokenizer_config.json`
5. **Shared embeddings:** The real Q4_0 GGUF includes `output.weight` Q8_0; keep the shared-embeddings fallback for other variants
6. **Large files:** Map per tensor (do not assume a small size)
7. **Correctness false positive:** Verification against references, not just visual inspection

## Review corrections

- The GGUF v3 header does not contain an alignment integer after `metadata_kv_count`; the alignment is the metadata `general.alignment`, with default 32.
- The tensor offset in the table is relative to the start of the data. `GgufTensorInfo.getOffset()` represents the absolute address in the file; `getRelativeOffset()` keeps the descriptor value.
- `dims[]` is preserved in GGML order; the loader reverses the order, confirmed by the matrix weights of the real file.
- `GgufType` in this implementation enumerates only the types accepted by the slice (F32, F16, BF16, Q4_0 and Q8_0).
- The real GGUF has 291 tensors and includes `output.weight` Q8_0; the earlier claim of always-shared embeddings was wrong.
- Tokenizer parity was tested earlier (identical IDs on the six texts). Smoke F16/Q8_0/Q4_0 passed and recorded identical 31-character golden answers. This confirms only this short prompt, not a long generation; the weight divergence is analyzed in the factual review below.

## Factual review (2026-10-16)

- The old half-step criterion for the quantized weights against F16 was inadequate as proof of the repack and was replaced in spec §6 item 3 by independent dequantization of the GGML bytes and exact equality with the loader. The F16 statistic does not fail the test.
- The hypothesis that the 6.17 steps in `embed_tokens` were only quantization/imatrix is refuted for that point: the Q4 access used multiplication by `1/32` in `float`, which loses precision at large indices. The block address now uses integer division. The provenance/imatrix of the GGUFs was not confirmed.
- Real Q4 verification: 169 Q4_0 tensors / 493 961 216 values and 1 Q8_0 tensor / 136 134 656 values, exact equality; Q4/F16 mean 0.24477 steps, maximum 1, 99.4083% within half a step, 10 179 596 saturated, the rest within half a step.
- Real Q8 verification: 170 tensors / 630 095 872 values, exact equality; Q8/F16 mean 0.24274 steps, maximum 0.67213, 99.2894% within half a step.
- The three smoke runs passed at 0 °C with `-XX:MaxDirectMemorySize=4g`; all answered `The capital of France is Paris.`. The common prefixes F16/Q8_0 and F16/Q4_0 are 31 characters (the whole answer); the prompt ends early, so it does not measure divergence in a long generation.
- F16 uses direct memory: the GGUF has 1 266 425 696 bytes and is widened to about 2.53 GB; documented in `docs/backends.md`. The default limit of ~1.94 GB failed and the test was run with a 4g limit. Arena requires explicit ownership/lifetime of the weights and was not tested.
