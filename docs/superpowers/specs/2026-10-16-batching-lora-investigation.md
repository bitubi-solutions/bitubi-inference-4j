# Investigation: continuous batching and LoRA adapters

Date: 2026-10-16. Scope: reading the `bitubi-inference-4j` code; no changes to the engine. Section 7 of `2026-10-12-engine-direction-decisions.md` states these questions as hypotheses still to be validated.

## Summary

- **Continuous batching:** the engine already computes several positions of a single prompt in a batch of up to `max_batch_size` tokens, and keeps a separate KV per session UUID. I did not find a scheduler that interleaves sessions, nor batching of independent requests. The REST endpoint can receive concurrent calls; that does not prove it is safe for simultaneous inference. The state of `CausalSelfAttention` and `MLPBlock` contains shared temporary arrays, and the KV of the same session has no lock. The prudent conclusion is: distinct sessions have partial isolation and share the CPU computation, but concurrency safety is not established; two calls on the same session can contend for the position and the KV write.
- **LoRA:** generic SafeTensors can be read, but I did not find a PEFT reader, interpretation of `adapter_config.json`, mapping of the LoRA tensor names, or application of A/B in the layers. `WeightLoader` is a natural entry point for locating tensors, but applying the adapter needs an adapter context at execution time and a change to the linear projection or a wrapper around the weights. The cost depends on the rank and the target matrices. Merging per client removes the LoRA cost at inference, but duplicates the base weights per client if distinct merged models are kept.

## Facts observed in the code

### 1. Concurrency and batching

- `AbstractModel` has a single `KvBufferCache` per instance and creates `TransformerBlock[]` and layers in the constructor; the weights/layers are therefore shared among the calls made to the same instance ([AbstractModel.java:86-118](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L86), [AbstractModel.java:170-175](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L170)).
- `KvBufferCache` keeps `UUID -> KvBuffer` in a `ConcurrentHashMap`, creating one buffer per session; the buffer keeps the context position in an `AtomicInteger` ([KvBufferCache.java:48-64](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/KvBufferCache.java#L48), [KvBufferCache.java:197-222](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/KvBufferCache.java#L197)). `getKvBuffer` returns the same buffer for the same UUID. There is no per-session lock in that code.
- The KV pages are created on lazy demand, but the `pages` arrays and the operations that check/create/assign pages are plain, with no synchronization ([KvBufferCache.java:205-209](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/KvBufferCache.java#L205), [KvBufferCache.java:307-320](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/KvBufferCache.java#L307), [KvBufferCache.java:331-351](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/KvBufferCache.java#L331)). Concurrent calls on the same session can read the same position and write to the same pages.
- `generate` obtains the KV per session and reads the position at the start, but does not reserve the position atomically with the generation; it increments it token by token in the decode loop ([AbstractModel.java:520-525](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L520), [AbstractModel.java:577-588](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L577)).
- The existing `batchForward` slices **the tokens of one prompt** into blocks of `MAX_BATCH_SIZE` (default 256) and routes each block to `forward`; it does not aggregate prompts of different sessions ([AbstractModel.java:58](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L58), [AbstractModel.java:269-299](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L269)). `generate` first does that batched prefill and then decodes token by token for a single session ([AbstractModel.java:549-560](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L549), [AbstractModel.java:577-588](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/AbstractModel.java#L577)).
- Transient tensors are obtained through the static `TensorCache`, which has concurrent queues per shape and clears the tensor when it is returned; the cache allows reuse across threads, but that does not protect temporary references still in use ([TensorCache.java:28-34](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/TensorCache.java#L28), [TensorCache.java:75-110](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/tensor/TensorCache.java#L75)).
- There are mutable arrays in the shared layer objects: `CausalSelfAttention.qkvResults` is filled with tensors local to the call and read by parallel work; `MLPBlock.batchResults` follows the same pattern ([CausalSelfAttention.java:56-57](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/CausalSelfAttention.java#L56), [CausalSelfAttention.java:149-175](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/CausalSelfAttention.java#L149), [MLPBlock.java:45-46](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/MLPBlock.java#L45), [MLPBlock.java:100-119](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/MLPBlock.java#L100)). Two concurrent calls on the same instance can replace the references in those arrays while the parallel work is using them.
- The current parallelization is mostly **inside one operation**: `PhysicalCoreExecutor` wraps a shared `ForkJoinPool` and waits with `join`; there are also `VectorMath.pchunk`/parallel streams used by the kernels and layers ([PhysicalCoreExecutor.java:26-60](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/util/PhysicalCoreExecutor.java#L26), [CausalSelfAttention.java:156-175](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/CausalSelfAttention.java#L156)). This is not a session pool with continuous batching.
- In the OpenAI REST layer, the service creates a random UUID by default, accepts `X-Bi4j-Session`, and calls `model.generate` directly on the non-streaming request. On the streaming path it uses `CompletableFuture.supplyAsync`, so streaming requests can be dispatched concurrently; there is no queue/model scheduler in this controller ([OpenAIChatService.java:38-47](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L38), [OpenAIChatService.java:65-76](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L65), [OpenAIChatService.java:109-129](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L109), [OpenAIChatService.java:159-171](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L159)). The concrete web executor and its limits were not determined in this reading.

### 2. SafeTensors and LoRA integration points

- `WeightLoader` exposes metadata, a tensor map, `isWeightPresent`, `load(...)` and dtype. It has no interface for adapters, loader composition or client/adapter identity ([WeightLoader.java:23-40](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/safetensors/WeightLoader.java#L23)).
- `SafeTensorSupport.loadWeights` recognizes the standard sharded index and `model.safetensors`; otherwise it fails. It does not look for PEFT `adapter_model.safetensors` or `adapter_config.json` ([SafeTensorSupport.java:112-123](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/safetensors/SafeTensorSupport.java#L112)). `SafeTensorIndex` reads tensor names and data from the files referenced by the index, but gives them no LoRA semantics ([SafeTensorIndex.java:83-119](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/safetensors/SafeTensorIndex.java#L83)).
- The model loads the named weights when building the layers. In Llama, for example, `q_proj`, `k_proj`, `v_proj`, `o_proj` and the MLP projections become fields of `CausalSelfAttention`/`MLPBlock` ([LlamaModel.java:98-142](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/llama/LlamaModel.java#L98)). The `WeightLoader` can supply additional tensors, but the current consumers neither request nor apply `lora_A`/`lora_B`.
- The REST layer keeps a single `Generator model` reference injected into the service; the request chooses a session by header, not an adapter id ([OpenAIChatService.java:46-47](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L46), [OpenAIChatService.java:65-76](../../../bitubi-inference-4j-net/src/main/java/ao/bitubi/inference4j/net/openai/OpenAIChatService.java#L65)). I did not observe any routing from client to weights/adapter.

## Inference and technical opinion (not measured facts)

### Continuous batching

**Answer:** there is token batching in the prefill of one generation; there is no multi-session continuous batching implemented as a feature. Several requests can reach the REST layer and start work at the same time, but the code observed does not provide enough reentrancy guarantees for the same layers. In particular, the shared temporary arrays indicate a possible race even with distinct UUIDs; the same session adds a position and KV race. The fact that the persistent weight tensors are final fields in most layers allows sharing them in principle, provided the temporaries become local to the call and the KV has a well-defined owner/synchronization.

**Estimated effort:** medium to high. First, fix/review reentrancy (local temporary arrays, a concurrency test with deterministic outputs, a policy for simultaneous calls on the same session). Then implement a per-model scheduler: bounded queue, per-request sequence state, selection of active sessions, prefill in variable batches, per-token decode in rounds, management of context lengths/KV, and cancellation/backpressure in the REST layer. The attention path today receives a tensor with a batch of contiguous tokens and a common starting position ([CausalSelfAttention.java:140-147](../../../bitubi-inference-4j-core/src/main/java/ao/bitubi/inference4j/model/CausalSelfAttention.java#L140)); sessions with different lengths and positions require per-element indices/positions/KV or grouping by compatibility. This is a change to the contract of the attention paths and kernels, not just a queue in the controller. There is no benchmark nor an estimate in days in this investigation.

### LoRA

**Answer:** the existing SafeTensors reading provides reusable blocks, but PEFT LoRA loading and execution are not implemented on the path observed. The narrowest point to integrate the reading would be a loader/composer over `WeightLoader`; the computation point sits next to the linear projections in the layers (attention and MLP), to add `scale * (x Aᵀ) Bᵀ` per active adapter. It is necessary to normalize PEFT names (including name variants and target modules), validate rank/shape/alpha, and define dtype/quantization before loading. Applying the delta before quantizing to the weight format may not be equivalent to applying LoRA at runtime over quantized weights; this needs a decision and a quality test.

For a target matrix of dimension `out × in` and rank `r`, A+B contain `r(in+out)` parameters. Approximate raw memory per target: `r(in+out) × bytesPerParameter` (2 bytes in BF16/FP16, 4 in F32), plus metadata/overheads. For example, with `in=out=4096`, `r=16`, BF16, that is about 256 KiB per target matrix; multiply by the number of adapted projections and layers and by the number of resident clients/adapters. This is a calculation from the formula, not a runtime measurement. At execution time, two low-rank projections are added per target and token; the cost grows as `O(r(in+out))` per token/target, on top of the base GEMM. Grouping requests with different adapters requires selecting and summing the correct deltas per batch element, which overlaps with the continuous batching work.

**Merging per client:** merge computes `W' = W + scale·BA` once and uses the current weight path; it does not pay the two additional projections per token. If each client has its own merged model in memory, it duplicates the base weights and may also require a new quantize/load per client. If it merges temporarily and stores to disk, it reduces the repeated startup cost, but there is still per-client storage and no real sharing of the base tensor during execution. The option is operationally simpler and more predictable for a few active adapters; runtime LoRA is more memory-efficient when there are many small adapters over one base, but needs more changes and measurement.

## Risks and points to verify

- The races on the temporary buffers are inferred from shared fields and use in parallel lambdas; no concurrent test was run to demonstrate corruption. To be safe, do not assume production support for parallel calls on the same instance until reentrancy is proven.
- The conclusions about `bitubi-inference-4j-net` cover the OpenAI controller analyzed; they do not determine the limits of the servlet container, all routes, or the behavior of other servers/endpoints.
- The exact compatibility of the PEFT adapter names/configs accepted by the product was not verified, nor the ability to merge adapters for each dtype/quantization present.
- Throughput, latency, resident memory per session/adapter and LoRA overhead were not measured.

## Recommended next steps

1. Before promising concurrency, write a concurrent test with two distinct sessions and two calls on the same session; make layer temporaries local and define serialization/position reservation per session according to the results.
2. Do a multi-session scheduler spike limited to one architecture (Llama), using the existing per-session KV. Measure throughput/latency against the current concurrent requests and include interleaved prefill/decode before generalizing the layer APIs.
3. Do an inference LoRA spike for one architecture and one concrete PEFT adapter: validate config/names/shapes, start with `q_proj` and `v_proj`, compute memory from the rank, compare logits/quality and tok/s between base, runtime LoRA and merge.
4. Only then decide the product contract: a safe adapter identifier per request/client, cache/eviction and limits on resident adapters; the existing session key must not be reused as adapter identity.
